# Sshd4a Fork — техническая спецификация

Форк проекта [tfonteyn/Sshd4a](https://github.com/tfonteyn/Sshd4a). Апстрим явно запрещает root-функциональность
("Please do NOT request implementing some sort of root access. Such requests will be closed immediately") —
поэтому всё нижеописанное реализуется **только в собственном форке**, не как PR в оригинальный репозиторий.

**minSdkVersion: 30 (Android 11)** — совпадает с текущим требованием апстрима, дополнительных ограничений не вводит.

---

## 1. Модель пользователей

Три класса пользователей SSH-сессии:

| Пользователь | Контекст выполнения | HOME |
|---|---|---|
| обычный | app UID (как сейчас в Sshd4a) | app-sandbox / текущий дефолт |
| shell | через `su`/эскалацию с ADB shell UID (2000) | `/data/local/tmp/Sshd4a/shell/home/` |
| root | через `su` с UID 0 | `/data/local/tmp/Sshd4a/root/home/` |

### 1.1 Обработка `su`

На части устройств (подтверждено: 32-bit ARM) `su -c "<cmd>"` не работает, нужен позиционный синтаксис
`su 0 sh -c "<cmd>"`.

**Решение — пробник su при первом root-логине на устройстве:**

1. По очереди пробуем шаблоны:
   - `su -c "%CMD%"`
   - `su 0 sh -c "%CMD%"`
   - `su root -c "%CMD%"`
2. Критерий успеха: exit code 0 и `id` в выводе показывает `uid=0`.
3. Рабочий шаблон кэшируется (DataStore/SharedPreferences), привязан к устройству, не к сборке.
4. В настройках — ручное переопределение шаблона на случай, если пробник ошибся.

## 2. Домашние директории и зеркалирование утилит

```
/data/local/tmp/Sshd4a/
├── root/home/          ← HOME root-пользователя
├── shell/home/         ← HOME shell-пользователя
├── bin/                ← общие утилиты (доступны всем, включая обычного пользователя)
├── etc/                ← общие конфиги (в т.ч. terminfo для tmux)
└── exec/               ← служебная папка для EXEC-команд (см. §4)
```

**Важный технический риск (требует эмпирической проверки, не закладывать как гарантию):**
процесс приложения работает под app UID, а не под shell/root. Запись в `/data/local/tmp/*`
делают только root/shell-сессии — у них есть право. Но сможет ли **сам процесс приложения**
(для обслуживания sftp/shell обычного пользователя) *прочитать* эти файлы — зависит от
SELinux-политики конкретного устройства/прошивки.

→ Перед реализацией: собрать диагностику с устройства —
`ls -laZ /data/local/tmp`, `getenforce`, тест чтения файла из-под обычного (не su) процесса.
По результатам, возможно, потребуется `chcon`/`chmod` после каждого копирования в root-скрипте.

## 3. Пакетный менеджер утилит ("pkg")

### 3.1 Формат индекса (`index.json`)

```json
{
  "repo_name": "sshd4a-default",
  "format_version": 1,
  "packages": [
    {
      "name": "htop",
      "version": "3.3.0",
      "arch": ["armeabi-v7a", "arm64-v8a"],
      "url": {
        "armeabi-v7a": "https://.../htop-armv7",
        "arm64-v8a": "https://.../htop-arm64"
      },
      "sha256": {
        "armeabi-v7a": "...",
        "arm64-v8a": "..."
      },
      "install_path": "bin/htop",
      "size_bytes": 182344,
      "post_install": null
    }
  ]
}
```

### 3.2 Дефолтные (встроенные) репозитории

Курируемый **собственный** индекс (не автосбор через GitHub Releases API — надёжнее и не зависит
от соглашений об именовании в чужих репах). Источники для наполнения индекса:

- **bnsmb/binaries-for-Android** — активно поддерживается, arm64-v8a: bash-static, 7zz, gdb, htop, tmux, openssh.
- **Zackptg5/Cross-Compiled-Binaries-Android** — curl (boringssl), сетевые утилиты.
- **bol-van/bins** — mc, openssh-сервер, fallback-источник.

Индекс размещается как статический `index.json` в отдельном публичном репозитории/gh-pages,
раздаётся анонимно через `raw.githubusercontent.com` — **GitHub-токен в самом приложении не нужен**.
Токен нужен только на стороне поддержки индекса (например, GitHub Actions для полуавтоматической сборки),
и то не обязателен на старте — можно вести вручную.

### 3.3 Клиентская логика

1. Архитектура устройства определяется через `Build.SUPPORTED_ABIS` (не через `uname`).
2. Список репозиториев — настраиваемый, каждый репозиторий можно **включить/выключить чекбоксом**
   в настройках (на случай, если источник перестанет существовать).
3. `pkg update` — скачивает и кэширует все включённые индексы.
4. `pkg install <name>` — качает нужный ABI-вариант, сверяет sha256, `chmod +x`, кладёт в `bin/`.
5. `pkg list` / `pkg remove` — без резолвинга зависимостей (бинарники статические).
6. Добавление своего репозитория: `pkg repo add <url>` → валидация схемы `index.json` → добавление в список.

## 4. Внешнее управление (автоматизация — MacroDroid, TVQuickActions, ADB, Tasker)

### 4.1 Уже есть в апстриме (сохраняем)

```
am start -a com.hardbacknutter.sshd.fg.START
am start -a com.hardbacknutter.sshd.fg.STOP
```
Включается опцией "Allow starting the service by an external Intent". Без дополнительной защиты
(апстримная документация прямо это указывает) — сохраняем поведение как есть для совместимости.

### 4.2 Новое: EXEC-интент (выполнение произвольных команд)

Отдельный intent action, например `com.hardbacknutter.sshd.fg.EXEC`:

- Extras: `--es cmd "<command>"`, `--es exec_as "root|shell|user"`, опционально `--es cwd`.
- **Настройка в UI — простая галочка** "Allow external command execution" с обязательным
  предупреждающим диалогом при включении (аналог термуховского "you understand the risk").
- **Токен — опционально, по выбору пользователя** ("на свой страх и риск", как в Termux F-Droid):
  генерируется случайная строка, показывается в UI, пользователь вставляет её в extra-параметр
  вызывающего приложения (`--es token XXXXXXXX`). Без корректного токена (если включён) — intent игнорируется.
  Без токена — работает открыто, как текущий START/STOP.
- Результат выполнения (т.к. синхронный ответ через `am broadcast` не поддерживается Android):
  через `ResultReceiver`/`PendingIntent`, переданный вызывающей стороной, либо запись в
  `.../Sshd4a/exec/last_result.txt` + broadcast-уведомление о завершении (удобно для Tasker/MacroDroid).

## 5. Интеграция с Termux (`termux` / `tmx`)

### 5.1 Определение поддержки

Официальные **F-Droid и GitHub** сборки Termux (общий sharedUserId `com.termux`) поддерживают
**RUN_COMMAND Intent**. **Play Store версия** (неофициальный форк, maintainer fornwall) —
RUN_COMMAND и связанные permissions **физически удалены** из-за политик Google.

Проверка: `PackageManager.getPackageInfo("com.termux", GET_PERMISSIONS)` →
ищем объявление `com.termux.permission.RUN_COMMAND`. Если отсутствует — сообщаем
пользователю, что интеграция невозможна с установленной версией Termux.

### 5.2 Команда `termux` / `tmx` внутри SSH-сессии

**Root/shell-сессия** — полноценный интерактивный вход, через собственный `login` Termux
(не дублируем его env-переменные вручную — используем его же логику):

```
su 0 sh -c "/data/data/com.termux/files/usr/bin/login"
```
(с учётом кэшированного su-шаблона из §1.1). Даёт полноценную PTY-сессию, привязанную к SSH.

**Обычный (non-root) пользователь** — ограниченный режим через RUN_COMMAND:

- Требует: `allow-external-apps = true` в `~/.termux/termux.properties` Termux
  (пользователь включает сам — мы не можем без root) + однократный grant разрешения
  `com.termux.permission.RUN_COMMAND` нашему приложению.
- Каждая введённая после `termux`/`tmx` команда — отдельный RUN_COMMAND в background-режиме,
  результат прилетает через PendingIntent и печатается в SSH-сессию.
- **Не настоящий интерактивный шелл**: нет job control, `cd` эмулируется вручную
  (храним "текущую директорию" и подставляем в каждую следующую команду).
- Ограничения явно отражаются в UI/документации.

## 7. Открытые вопросы / следующие шаги

1. Диагностика конкретного устройства: `su`-шаблон, SELinux-права на `/data/local/tmp`, наличие
   рабочей сборки nano под 32-bit ARM.
2. Черновик протокола EXEC (плоские `--es` extras vs JSON-строка в одном extra) — не финализирован.
3. Наполнение стартового `index.json` — конкретные версии/ссылки на assets из трёх источников (§3.2).
4. UI-флоу для EXEC-токена и предупреждающих диалогов (root, EXEC, pkg-репозитории).
5. Сборка окружения: кросс-компиляция через Android NDK там, где готовых статических бинарников нет
   или они не подходят под конкретный ABI/32-bit устройства.

## 8. Дальнейшая работа над кодом

Эта песочница (bash-инструмент) не имеет доступа к Android SDK/NDK и Google-репозиториям
(разрешённые сетевые домены ограничены пакетными менеджерами вроде npm/pip/cargo и GitHub) —
собрать APK здесь не получится. Реальная разработка/сборка форка — на твоей машине или через
**Claude Code**, где есть полноценный доступ к NDK/Gradle/эмулятору. Могу помогать точечно:
писать конкретные файлы (Kotlin/Java-классы, CMake/NDK-скрипты, layout-файлы), которые ты
будешь собирать локально, или разбирать структуру исходников апстрима файл за файлом, когда
будет доступ к клонированному репозиторию.
